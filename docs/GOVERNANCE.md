# docs 文档治理规范（GOVERNANCE）

> 本文档定义 `docs/` 目录的**更新规范、命名约定、目录落位规则与版本控制机制**，供所有贡献者与 AI Agent 遵循。
> 配套：导航索引见 [README.md](./README.md)；ADR 模板见 [adr/README.md](./adr/README.md)。

## 1. 目标

1. **单事实源（Single Source of Truth）**：同一信息只在一处维护，其余引用指向它（对齐 [optimize.md](./optimize.md) F10）。
2. **快速定位**：任何信息按「分类 → 索引 → 文档」三步可达（每子目录有 `README.md` 索引）。
3. **可维护**：静态真相源（架构/方案）与动态状态（任务/进度）分离，避免高频更新污染低频引用。
4. **可扩展**：新文档按规则落位，不破坏既有链接（`docs/` 内**禁止移动文件而不修引用**）。

## 2. 文档生命周期

| 阶段 | 动作                                       | 触发条件                | 示例               |
| :--- | :----------------------------------------- | :---------------------- | :----------------- |
| 创建 | 新建 `.md` + 更新所属目录 `README.md` 索引 | 新信息无法并入现有文档  | 新生态包方案       |
| 更新 | 编辑内容 + 「最近更新」或 changelog 记录   | 事实变化 / 任务状态变化 | 任务完成、评估刷新 |
| 归档 | 移入 `info/` 或标注 `状态：已归档`         | 一次性报告、历史快照    | reka-ui 同步报告   |
| 删除 | 删除文件并移除全部引用                     | 内容被合并 / 彻底过时   | —                  |

> **创建前置检查**：先判断能否**并入现有文档**（改文档），再判断是否**新建文档**。只有跨领域、独立生命周期、被多处引用的内容才新建。

## 3. 命名规范

### 3.1 目录

| 目录              | 内容                             | 必带索引            |
| :---------------- | :------------------------------- | :------------------ |
| `docs/`（根）     | 跨领域核心文档（架构/路线/任务） | `README.md`（已建） |
| `docs/adr/`       | 架构决策记录                     | `README.md`         |
| `docs/ecosystem/` | 生态扩展包方案 + 商业化          | `README.md`（已建） |
| `docs/research/`  | 市场/竞品调研                    | `README.md`         |
| `docs/info/`      | 一次性/周期报告                  | `README.md`         |

> 注：组件检查 / 审计（D1–D7）的**方法与交付面**由组件开发技能 `.agents/skills/vean-ui-develop/audit.md` 定义，历史检查报告（`docs/check-reports/`、`docs/check.md`）已于 2026-08-14 清理归档，不再在 `docs/` 维护。

### 3.2 文件命名

- **一律 `kebab-case`**：`ui-shell-roadmap.md`、`reka-ui-sync-report.md`。
- **序号前缀左对齐补零**：ADR 用 `NNNN-`（四位）；组件检查报告用 `CXX-`（两位）。
- **不带头部冗余词**：避免 `docs-`、`final-`、`new-` 等前缀；版本/日期写在文档头部而非文件名（除非该文件为不可变快照，如 `info/` 报告可带日期）。

### 3.3 内容头部约定

每个文档首部应有（至少两项）：

```markdown
# 标题

> 定位：一句话说明该文档是什么、给谁看。
> 状态：✅ 已实施 / 🔵 进行中 / 📋 待排期 / 🗄️ 已归档 / 💡 提案
> 基线：YYYY-MM-DD · 分支：xxx
```

## 4. 目录落位决策树

```
新信息要落盘
 ├─ 属于「已接受的决策」？ ─────────────────► docs/adr/NNNN-*.md
 ├─ 属于「生态包方案 / 商业化」？ ──────────► docs/ecosystem/
 ├─ 属于「市场 / 竞品调研原始结论」？ ──────► docs/research/
 ├─ 属于「一次性 / 周期审计报告」？ ────────► docs/info/
 └─ 其余跨领域核心文档 ───────────────────► docs/ 根（且须在 README.md 登记）
```

> 判据要点：**根目录只保留被全局引用、跨领域的文档**；领域性内容一律进子目录。拿不准时问：删掉这份文档的目录前缀，读者还能从根导航找到它吗？

## 5. 更新规范

### 5.1 静态真相源 vs 动态状态（关键分离）

| 类型       | 文档                                              | 更新频率           | 更新规则                                                          |
| :--------- | :------------------------------------------------ | :----------------- | :---------------------------------------------------------------- |
| 静态真相源 | architecture / optimize / 领域路线图 / 提案 / ADR | 低频（事实变化时） | 由架构评审驱动；改后同步所有引用                                  |
| 动态执行   | （不设常驻文档）                                  | —                  | 任务拆解与状态走 issue / 临时计划；需要沉淀的结论回填路线图或 ADR |

> **docs/ 不保留常驻的任务拆解/状态跟踪文档**（2026-09 起 tasks.md / task-tracking.md / ecosystem-tasks.md 已废止，经 git 历史追溯）：执行状态天然高频漂移，历史教训是状态表与实际很快脱节。
>
> 组件级状态与检查由组件开发技能（`.agents/skills/vean-ui-develop/`）统一管理，不落 `docs/`。

### 5.2 单事实源清单

| 事实           | 唯一权威文档/文件                                       |
| :------------- | :------------------------------------------------------ |
| 工作区架构     | `docs/architecture.md`                                  |
| 工程质量改进项 | `docs/optimize.md`（F1–F11）                            |
| 组件评估明细   | `docs/roadmap.md`                                       |
| 核心内领域规划 | `docs/ui-ai-roadmap.md` · `docs/ui-shell-roadmap.md`    |
| 组件审计方法   | `.agents/skills/vean-ui-develop/audit.md`（D1–D7）      |
| 未来领域提案   | `docs/ecosystem/`（每方向一篇，立项时确定落地形态）     |
| 商业化策略     | `docs/ecosystem/commercialization.md`（方向与横向建议） |
| 调研结论       | `docs/research/`                                        |

### 5.3 交叉引用维护（强制）

- **移动/重命名任何 `.md`**：必须全仓 `grep` 旧路径并更新所有引用（`docs/` 内部、根 `README.md`、`AGENTS.md`、`CONTEXT.md` 等），否则不得提交。
- **删除文档**：同时删除其全部入链。被删内容若有长期参考价值，先迁移到 `info/` 归档；**已取消/过期的规划与任务跟踪文档直接删除**（git 历史即可追溯，不留横幅副本）。
- **建议**：引用时优先写「相对路径 + 锚点」（如 `[optimize.md](./optimize.md#6-不建议立即执行的方案)`），移动后便于批量修正。

## 6. 版本控制机制

### 6.1 Git 提交规范

- 文档变更与代码变更**同仓、同分支**，随功能提交；纯文档改动用 `docs(scope): <描述>` 前缀（scope 取 `roadmap`/`ecosystem`/`adr` 等）。
- 提交信息须说明「改了哪份文档、为什么」，如：
  - `docs(ecosystem): add @soybeanjs/table proposal`
  - `docs(roadmap): fix broken check.md link after docs reorg`
- **不提交生成物冲突**：`apps/docs/src/generated/` 下的生成文件由 `pnpm sui *` 命令统一产出，勿手工改（见根 `AGENTS.md`）。

### 6.2 版本与快照

- 文档**不单独编号**：以仓库 lockstep 版本 + 文档头部「基线日期」为准。
- **不可变快照**（`info/` 报告、ADR 已接受条目）一经落盘不改历史内容；修订通过「新增后续条目」表达，不覆盖原文。
- 需要追溯时依赖 git 历史；**不在文档内维护多版本副本**。

### 6.3 分支合并注意点

- 功能分支短命化：不长期维护与 `main` 平行的集成分支（2026-08 的 `ecosystem` / `ui-x` / `admin` 分支均已归档，相关包已取消/移除）。
- 合并前：确认 `docs/README.md`、各子目录 `README.md` 与目标分支的文档集一致；文档冲突优先取「内容完整、链接可解析」的一方，再补修引用。

## 7. 合并前检查清单（Checklist）

- [ ] 新文档已登记到所属目录 `README.md`
- [ ] 全文无 `TODO`/占位未定内容（提案类除外，须标注状态）
- [ ] 移动/重命名后全仓引用已更新（`grep` 旧路径为空）
- [ ] 任务/检查类文档的「最近更新」已追加记录
- [ ] 生成文档（generated/*）未被手工修改
